# 协同通讯录共享后端对接说明

维护位置：`docs/协同通讯录共享后端对接说明.md`

交接日期：2026-05-19

面向对象：后端经理、workspace 后端接口负责人

## 前端已完成

本轮前端只改通讯录 / 共享 / 协同相关 UI 和本地状态组织，不涉及其它业务模块，也没有要求后端立即改接口。所有新增交互仍尽量沿用现有 workspace API、现有字段和本地兼容逻辑；后端暂不变更时，页面可以继续运行，但部分数据仍需要前端从 `users`、`contacts`、`projects.members`、`memberRoles` 和 `templateShareInfo` 中本地拼装。

已完成的前端界面能力如下。

| 模块 | 本轮 UI 变化 | 当前数据来源 |
| --- | --- | --- |
| 协同成员弹窗 | 支持从通讯录批量选择成员，一次加入项目；支持按部门筛选、搜索、已选成员预览。 | `users` / `activeUsers`、项目 `members`、`memberRoles` |
| 项目成员管理 | 按权限分为“管理 / 编辑 / 只读”三组展示，支持调整成员权限和移除成员。 | `project.members`、`project.memberRoles` |
| 通讯录 | 支持部门树筛选、联系人搜索、关注状态展示和个人资料查看。 | `users` / `activeUsers`、`contacts` |
| 关注关系 | 支持关注 / 取消关注联系人。 | `GET /workspace/contacts`、`POST /workspace/contacts`、`DELETE /workspace/contacts/:contactId` |
| 通讯录个人详情 | 弹层展示姓名、部门、岗位、联系方式、邮箱、MBTI、头像、在线状态等信息。 | 用户对象兼容字段 |
| 模板共享 | 支持把共享成员分到“可编辑 / 只读”权限区，展示共享对象和权限。 | `templateShareInfo`、模板共享接口返回 |
| 顶部成员摘要 | 项目头部最多展示 3 个成员头像，并显示项目总人数或额外人数。 | 优先本地 `members` 计算，未来可读 `memberSummary` |

需要后端注意的是：这些能力当前是前端 UI 先行，很多映射和归一化还在前端兜底。后续如果后端提供标准结构，前端可以减少硬编码、减少多接口拉取，并降低多端协同时的状态不一致。

### 统一口径（本次交接必须保持）

- 前端改动范围仅限通讯录、共享、协同。
- 部门展示顺序固定为：项目管理、AIGC、美术设计、三维动态、动效设计、视效包装。
- 通讯录 / 共享 / 协同场景里，历史“后期合成”部门统一按“视效包装”展示。

## 建议后端改造

后端建议按“先补数据结构，再补批量写接口，最后优化列表摘要”的顺序改造。前端可以兼容旧字段，因此后端可以灰度上线，不需要一次性切断旧格式。

| 优先级 | 能力 | 后端改造目标 |
| --- | --- | --- |
| P0 | 部门树 canonical key 与展示名映射 | 返回稳定的部门唯一键、展示名和别名映射，避免前端继续硬编码部门名称。 |
| P0 | 固定部门顺序与后期合成映射 | 部门树接口返回稳定排序字段（或显式顺序）并统一把“后期合成”映射到“视效包装”。 |
| P0 | 项目协同成员批量加入 / 移除 | 支持一次写入或移除多个成员，后端做幂等、去重和权限校验。 |
| P0 | 权限分组管理 / 编辑 / 只读 | 后端统一接受 `manager`、`editor`、`readonly` 三类项目角色，并返回最终分组结果。 |
| P1 | 关注 / 取消关注 | 明确当前用户与目标用户的关注关系模型，返回可用于前端刷新状态的最终对象。 |
| P1 | 通讯录个人详情 | 提供联系人详情接口，避免前端只靠列表数据拼详情。 |
| P1 | 模板共享成员与权限 | 统一模板共享成员结构，权限只保留 `edit`、`read`，返回规范化后的共享列表。 |
| P2 | 顶部成员摘要最多 3 个 + 总数 | 项目列表和项目详情可直接返回轻量成员摘要，避免头部场景加载完整成员表。 |

权限校验必须在后端完成。前端按钮隐藏只代表 UI 限制，不能作为写接口的安全边界。项目成员写入建议只允许项目 `manager`、超级管理员或后端认可的项目管理角色执行；模板共享建议只允许模板 owner 或有 `edit` 权限的成员调整。

## 数据结构建议

### 部门树 canonical key 与展示名映射

部门需要同时返回稳定的 canonical key 和展示名。canonical key 用于筛选、存储和接口传参，展示名用于 UI 文案；展示名未来改名时，不应影响历史数据和筛选逻辑。

部门 canonical key 同时建议固化顺序：`project-management`、`aigc`、`art-design`、`3d-dynamic`、`motion-design`、`effect-packaging`。前端按该顺序渲染部门树；若历史数据里仍有“后期合成”，请在后端映射到 canonical key `effect-packaging`，展示名统一为“视效包装”。

建议结构：

```json
{
  "departments": [
    {
      "id": "art-design",
      "key": "art-design",
      "departmentId": "art-design",
      "name": "美术设计",
      "displayName": "美术设计",
      "parentId": null,
      "count": 18,
      "aliases": ["美术", "设计中心"],
      "children": [
        {
          "id": "art-design-1",
          "key": "art-design-1",
          "departmentId": "art-design-1",
          "name": "美术设计一部",
          "displayName": "美术设计一部",
          "parentId": "art-design",
          "count": 9,
          "aliases": [],
          "children": []
        }
      ]
    }
  ],
  "departmentNameMap": {
    "art-design": "美术设计",
    "art-design-1": "美术设计一部"
  }
}
```

兼容字段建议同时保留 `id`、`key`、`departmentId`。前端后续优先用 `key`，旧逻辑仍可读取 `id` 或 `departmentId`。

### 通讯录用户与个人详情

通讯录列表建议返回足够支撑筛选和基础展示的轻量字段；个人详情接口再返回完整字段。用户主键统一使用 `userId`，同时兼容 `id`，避免不同接口用姓名匹配成员。

建议用户结构：

```json
{
  "id": "user-001",
  "userId": "user-001",
  "username": "zhangsan",
  "name": "张三",
  "displayName": "张三",
  "avatar": "张",
  "departmentId": "art-design-1",
  "departmentKey": "art-design-1",
  "department": "美术设计一部",
  "job": "设计师",
  "phone": "13800000000",
  "email": "zhangsan@example.com",
  "mbti": "INTJ",
  "role": "member",
  "status": "active",
  "isFollowed": true,
  "contactId": "contact-001"
}
```

建议个人详情在此基础上补充 `bio`、`skills`、`location`、`lastActiveAt`、`projects` 等字段。前端当前不会强依赖这些扩展字段，但后续详情弹层可以直接展示。

### 项目成员、权限分组和顶部摘要

项目成员建议从“姓名数组 + memberRoles map”逐步升级为结构化成员数组。旧字段可以继续返回，方便前端兼容。

建议项目成员结构：

```json
{
  "members": [
    {
      "userId": "user-001",
      "memberName": "张三",
      "displayName": "张三",
      "avatar": "张",
      "departmentId": "art-design-1",
      "department": "美术设计一部",
      "role": "manager",
      "status": "active",
      "joinedAt": "2026-05-19T10:00:00+08:00"
    }
  ],
  "memberRoles": {
    "张三": "manager"
  },
  "memberGroups": {
    "manager": ["user-001"],
    "editor": ["user-002"],
    "readonly": ["user-003"]
  },
  "memberSummary": {
    "items": [
      {
        "userId": "user-001",
        "name": "张三",
        "avatar": "张",
        "department": "美术设计一部",
        "role": "manager",
        "status": "active"
      }
    ],
    "total": 12,
    "extraCount": 9
  }
}
```

`memberSummary.items` 最多返回 3 个成员，`total` 返回完整成员数，`extraCount` 可由后端返回，也可由前端用 `total - items.length` 计算。项目列表接口只需要摘要；项目详情或成员管理弹窗再拉完整成员列表。

## 接口建议

### 部门树和通讯录

```http
GET /workspace/departments/tree
GET /workspace/contacts/users?departmentKey=&q=&status=
GET /workspace/contacts/users/:userId
```

`GET /workspace/departments/tree` 返回标准部门树、`departmentNameMap` 和可用于前端稳定渲染的顺序字段（或顺序数组）。`GET /workspace/contacts/users` 返回通讯录用户列表，支持按 `departmentKey`、关键词 `q` 和状态筛选。`GET /workspace/contacts/users/:userId` 返回个人详情。

通讯录列表建议由后端按当前登录用户权限裁剪。传入未授权的 `departmentKey` 或搜索关键词时，后端只返回授权范围内的数据，不应泄露其它部门联系人。

### 关注和取消关注

```http
GET /workspace/contacts
POST /workspace/contacts
DELETE /workspace/contacts/:contactId
DELETE /workspace/contacts/by-target/:targetUserId
```

关注请求建议：

```json
{
  "targetUserId": "user-001",
  "relationType": "care"
}
```

关注成功建议返回：

```json
{
  "contact": {
    "id": "contact-001",
    "contactId": "contact-001",
    "userId": "current-user",
    "targetUserId": "user-001",
    "relationType": "care",
    "createdAt": "2026-05-19T10:00:00+08:00"
  }
}
```

取消关注当前兼容 `DELETE /workspace/contacts/:contactId`。建议额外支持 `DELETE /workspace/contacts/by-target/:targetUserId`，方便前端在只有目标用户 id、没有 contactId 时取消关注。两个删除接口都应保持幂等：关系不存在时返回 200 或 204，不要报 500。

### 项目协同成员批量加入和移除

```http
GET /workspace/projects/:projectId/members
POST /workspace/projects/:projectId/members
DELETE /workspace/projects/:projectId/members
PATCH /workspace/projects/:projectId/members
PUT /workspace/projects/:projectId/members/groups
```

批量加入请求建议：

```json
{
  "members": [
    {
      "userId": "user-001",
      "memberName": "张三",
      "role": "readonly"
    },
    {
      "userId": "user-002",
      "memberName": "李四",
      "role": "editor"
    }
  ]
}
```

批量移除请求建议：

```json
{
  "members": [
    {
      "userId": "user-001",
      "memberName": "张三"
    }
  ]
}
```

批量权限更新请求建议：

```json
{
  "updates": [
    {
      "userId": "user-001",
      "memberName": "张三",
      "role": "manager"
    },
    {
      "userId": "user-002",
      "memberName": "李四",
      "role": "readonly"
    }
  ]
}
```

权限分组替换请求建议：

```json
{
  "groups": {
    "manager": ["user-001"],
    "editor": ["user-002"],
    "readonly": ["user-003"]
  }
}
```

后端需要对 `projectId + userId` 做幂等处理。重复加入不应报错；移除不存在成员不应报错；更新权限时只接受 `manager`、`editor`、`readonly`。写接口建议返回规范化后的最终状态：

```json
{
  "projectId": "project-001",
  "members": [],
  "memberRoles": {},
  "memberGroups": {
    "manager": [],
    "editor": [],
    "readonly": []
  },
  "memberSummary": {
    "items": [],
    "total": 0,
    "extraCount": 0
  }
}
```

### 模板共享成员与权限

```http
GET /workspace/templates/:templateId/shares
PUT /workspace/templates/:templateId/shares
DELETE /workspace/templates/:templateId/shares/:userId
```

替换模板共享列表请求建议：

```json
{
  "entries": [
    {
      "userId": "user-001",
      "userName": "张三",
      "permission": "edit"
    },
    {
      "userId": "user-002",
      "userName": "李四",
      "permission": "read"
    }
  ]
}
```

`PUT /workspace/templates/:templateId/shares` 建议定义为“替换当前模板完整共享列表”。后端保存前需要去重、校验用户是否存在、校验当前操作者是否有共享管理权限，并把权限归一为 `edit` 或 `read`。返回值建议使用“数据结构建议”里的模板共享结构。

### 顶部成员摘要

项目列表和项目详情建议增加可选字段 `memberSummary`，用于项目卡片、顶部头像堆叠和成员总数展示。

```json
{
  "memberSummary": {
    "items": [
      {
        "userId": "user-001",
        "name": "张三",
        "avatar": "张",
        "role": "manager",
        "status": "active"
      }
    ],
    "total": 12,
    "extraCount": 9
  }
}
```

规则是 `items.length <= 3`，`total` 必须是完整项目成员总数。前端会优先读取 `memberSummary`；如果没有该字段，则继续用完整 `members` 列表本地计算。

## 兼容注意事项

前端当前仍兼容旧字段，后端可以分阶段上线。项目对象仍可返回 `members: ["张三", "李四"]` 和 `memberRoles: { "张三": "manager" }`；通讯录联系人仍可返回 `id`、`username`、`name`、`department`；模板共享仍可返回 `sharedWith` 和 `permissions`。新字段上线后，前端会优先使用 `userId`、`departmentKey`、`recipients`、`memberSummary` 等结构化字段。

部门相关逻辑不要再依赖展示名作为唯一值。展示名可变，canonical key 不应变。历史数据里如果只有中文部门名，后端建议在响应中通过 `aliases` 或 `departmentNameMap` 做一次映射，逐步补齐 `departmentKey`。

成员相关写接口不要只按姓名处理。当前前端为了兼容旧数据仍会带 `memberName`，但后端主键应使用 `userId`。同名用户、改名用户、跨部门调动用户都需要通过 `userId` 保持稳定。

批量写接口建议返回最终状态，而不是只返回 `{ "ok": true }`。前端会做乐观更新，但拿到后端响应后应该能用最终 `members`、`memberRoles`、`memberGroups`、`recipients`、`permissions` 覆盖本地状态，避免多端协作时角色残留。

关注关系建议保持幂等。重复关注同一 `targetUserId` 可以返回已有关系；取消不存在的关注可以返回成功。这样前端在快速点击、刷新后状态重放、网络重试时不会出现误报。

权限值需要后端白名单校验。项目成员权限只接受 `manager`、`editor`、`readonly`；模板共享权限只接受 `edit`、`read`。未知权限值建议返回 400，并在错误体里给出可接受枚举。

顶部成员摘要是性能优化字段，不是完整权限来源。后端不能用 `memberSummary.items` 判断完整成员权限；涉及成员管理、权限判断、共享校验时仍应读取完整成员关系。
## 本次新增后端对接重点（经理必读）

### 1) 成员 `userId` 不能退化为姓名

- 后端写接口（项目成员增删改、模板共享写入）必须以 `userId` 作为主键匹配与落库。
- `memberName` 仅作为展示兼容字段，不得作为唯一键参与权限判断。
- 对同名用户、改名用户、跨部门调动用户，后端都应保持 `userId` 稳定识别。

### 2) `department` key 统一策略

- 所有联系人、成员、模板共享返回结构统一输出：`departmentKey`、`departmentId`、`department`（展示名）。
- `departmentKey` 为唯一稳定键；`department` 为可变展示文案。
- 历史“后期合成”统一映射到 `departmentKey = effect-packaging`，展示名统一“视效包装”。

### 3) 模板共享权限与用户校验

- `PUT /workspace/templates/:templateId/shares` 执行“整表替换”时，后端必须执行：
  1. 用户存在性校验（`userId` 有效）；
  2. 操作者权限校验（仅 owner 或具备 `edit` 权限者可改）；
  3. 权限白名单校验（仅 `edit` / `read`）；
  4. 去重（同一 `userId` 只保留一条，后写覆盖前写）。
- 失败应返回可读错误体（建议含 code + message + 可接受枚举）。

### 4) 实时数据 / 刷新契约

前端已按“乐观更新 + 后端最终态覆盖”实现，后端需保证以下契约：

- 所有成员/共享写接口返回最终态（不可仅 `{ "ok": true }`），至少包含：
  - 项目成员场景：`members`、`memberRoles`、`memberGroups`、`memberSummary`；
  - 模板共享场景：`recipients`、`permissions`。
- 幂等保证：重复提交、并发重放、刷新重试不会产生重复成员/重复共享记录。
- 推荐追加 `updatedAt`（或版本号）用于前端判断覆盖时序。

### 5) 前端已改字段与后端需同步点

已改前端字段读取优先级（后端请同步输出）：

- 成员：优先 `userId`，兼容 `id` / `memberName`。
- 部门：优先 `departmentKey`，兼容 `departmentId` / `department`。
- 模板共享：优先 `recipients` + `permissions`，兼容 `sharedWith`。
- 项目头部摘要：优先 `memberSummary`，无则回退本地 `members` 计算。

后端同步建议（最小上线集）：

1. 在现有接口补齐结构化字段，不破坏旧字段；
2. 批量写接口返回最终态对象；
3. 为共享/成员写接口增加严格权限与用户校验；
4. 统一部门 key 与历史映射。
